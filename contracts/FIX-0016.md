# CONTRACT: Las credenciales de WooCommerce viajan en la query string en el fallback 401/403
# ID: FIX-0016
# Status: RESOLVED
# Mode: LOOP
# Gate-Mode: STRICT

## Intent
FIX-0004 eliminó las credenciales de la URL del camino principal, pero dejó un fallback: si el header `Authorization: Basic` responde 401/403, la petición se reintenta con `?consumer_key=...&consumer_secret=...`. Esas URLs quedan en los logs del servidor web, en proxies/CDN, en el historial de red y en los reportes de error: el secreto se filtra justo en el caso en que la autenticación falla. Además el reintento duplica la petición fallida y oculta la causa real al usuario.

## Reproduction Steps
1. Ejecutar la app contra una tienda cuyo servidor no acepta Basic Auth en la REST API (configuraciones con `mod_security`, plugins de seguridad o hostings compartidos).
2. Conectar la tienda y buscar un producto por SKU.
3. Inspeccionar la petición de reintento: la URL contiene `consumer_key` y `consumer_secret`.
4. Revisar el access log del servidor: los valores aparecen en claro.

## Current Behavior
- `services/wooService.ts` (`makeWooRequest`): primer intento con `getAuthHeaders` (Basic Auth); si la respuesta es 401 o 403, reconstruye la URL concatenando `consumer_key` y `consumer_secret` sin codificar y reintenta con `fetch(fallbackUrl)`.
- `services/wooService.test.ts` tiene dos tests que **validan** ese fallback (`fallbackUrl` contiene `consumer_key=`), por lo que hoy el comportamiento es intencional y está cubierto.
- `validateConnection` sólo distingue "ok" de "Credenciales inválidas o acceso denegado a Productos.", sin explicar que el problema puede ser el header bloqueado por el servidor.
- `components/ConnectionModal.tsx` muestra `err.message` tal cual en el bloque de error.

## Expected Behavior
- Ninguna petición de la app lleva credenciales en la URL (ni en el camino feliz ni en el fallido).
- Cada request se intenta **una sola vez** con `Authorization: Basic`; no hay reintento con otra forma de autenticación.
- Un 401/403 produce un mensaje único, exportado y accionable que explica: credenciales inválidas **o** header bloqueado por el hosting/WAF, y aclara que por seguridad no se envían credenciales por URL.
- El modal de conexión muestra ese mensaje sin reinterpretarlo.
- El resto de los errores (red, 500, 404) conserva su mensaje actual: no se disfraza un fallo de servidor como problema de credenciales.

## Entities Affected
- `services/wooService.ts` — `makeWooRequest` (sin fallback), nuevo mensaje/constante de error de autenticación, `validateConnection` (mapeo 401/403).
- `services/wooService.test.ts` — eliminar los tests del fallback y cubrir el nuevo contrato.
- `components/ConnectionModal.tsx` — sólo si hace falta para mostrar el mensaje (hoy ya muestra `err.message`).

## Business Rules
- BR-001: `consumer_key` y `consumer_secret` nunca aparecen en una URL solicitada por la app.
- BR-002: La validación de HTTPS se mantiene antes de cualquier intento; no se relaja como compensación.
- BR-003: Un 401/403 se informa con causa y alternativa, sin reintento inseguro y sin segunda petición.
- BR-004: Los tests que afirmaban el fallback por query string se eliminan o se reescriben al nuevo comportamiento.
- BR-005: Existe un **único** mensaje exportado para el fallo de autenticación (constante) que usan el servicio y la UI; no se duplica el texto en varios archivos.
- BR-006: Un código distinto de 401/403 no usa el mensaje de autenticación.

## Acceptance Criteria
- AC-001: GIVEN un servidor que responde 401 al header Basic WHEN ejecuto `validateConnection` THEN se realiza **una sola** petición y su URL no contiene `consumer_key` ni `consumer_secret`.
- AC-002: GIVEN ese mismo escenario WHEN la conexión falla THEN el error lanzado es el mensaje único de autenticación (menciona el header `Authorization`, el hosting/WAF y que no se envían credenciales por URL).
- AC-003: GIVEN la suite de tests WHEN se ejecuta THEN ningún test afirma el fallback por query string (no hay aserciones con `consumer_key=`/`consumer_secret=` en URLs).
- AC-004: GIVEN un servidor que responde 500 o un error de red WHEN ejecuto `validateConnection` THEN el mensaje no es el de autenticación (no se confunde un fallo del servidor con credenciales inválidas).
- AC-005: GIVEN el modal de conexión WHEN `validateConnection` rechaza con 401/403 THEN el texto mostrado es exactamente el mensaje único exportado.
