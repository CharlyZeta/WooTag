# CONTRACT: Las credenciales de WooCommerce viajan en la query string en el fallback 401/403
# ID: FIX-0016
# Status: DRAFT
# Mode: GATE
# Gate-Mode: STRICT

## Intent
FIX-0004 eliminó las credenciales de la URL del camino principal, pero dejó un fallback: si el header `Authorization: Basic` responde 401/403, la petición se reintenta con `?consumer_key=...&consumer_secret=...`. Esas URLs quedan en los logs del servidor web, en proxies/CDN, en el historial de red y en los reportes de error; el secreto se filtra justo en el caso en que la autenticación falla.

## Reproduction Steps
1. Ejecutar la app contra una tienda cuyo servidor no acepta Basic Auth en la REST API (muchas configuraciones con `mod_security` o plugins de seguridad, también Hostinger/servidores compartidos).
2. Conectar la tienda y buscar un producto por SKU.
3. Inspeccionar la petición de reintento: la URL contiene `consumer_key` y `consumer_secret`.
4. Revisar el access log del servidor: los valores aparecen en claro.

## Current Behavior
`services/wooService.ts` (`makeWooRequest`): primera petición con `getAuthHeaders` (Basic Auth); si la respuesta es 401 o 403, reconstruye la URL concatenando `consumer_key` y `consumer_secret` sin codificar y reintenta. `services/wooService.test.ts` tiene un test que **valida** ese fallback, por lo que hoy el comportamiento es intencional y está cubierto.

## Expected Behavior
Ninguna petición de la app lleva credenciales en la URL. Si el servidor rechaza Basic Auth, la app falla con un mensaje explícito y accionable (por ejemplo: "Tu servidor no acepta autenticación por header; contactá al hosting"), sin reintentar con secretos en la URL.

## Business Rules
- BR-001: `consumer_key` y `consumer_secret` nunca aparecen en una URL solicitada por la app.
- BR-002: La app valida HTTPS antes de cualquier intento (ya implementado); no se relaja esa regla como compensación.
- BR-003: Un 401/403 se informa al usuario con causa y alternativa, sin reintento inseguro.
- BR-004: Los tests existentes que afirman el fallback por query string se actualizan al nuevo comportamiento.

## Acceptance Criteria
- AC-001: GIVEN un servidor que responde 401 al header Basic WHEN ejecuto `validateConnection` THEN ninguna URL solicitada contiene `consumer_key` ni `consumer_secret`.
- AC-002: GIVEN ese mismo escenario WHEN la conexión falla THEN el error mostrado explica el problema de autenticación y no hay reintento con credenciales en la URL.
- AC-003: GIVEN la suite de tests WHEN se ejecuta THEN no existe ningún test que afirme el fallback por query string.
