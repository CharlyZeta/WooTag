# CONTRACT: Aviso de cambios de precio y SKUs nuevos para reimprimir etiquetas
# ID: FEAT-0001
# Status: DRAFT
# Mode: GATE
# Gate-Mode: STRICT

## Intent
Al abrir WooTag con una tienda conectada, comparar el catálogo publicado completo contra un snapshot de precios guardado en Firestore y avisar qué productos cambiaron de precio o pasaron a estar visibles, para agregarlos a la hoja de impresión y reimprimir sus etiquetas de exhibición sin revisar el catálogo a mano. La detección es independiente de si el producto ya tuvo etiqueta impresa.

## Use Case
**Actor:** Usuario de WooTag con cuenta Firebase iniciada y una tienda WooCommerce activa.
**Goal:** Saber qué etiquetas de exhibición hay que reimprimir por cambios de precio o productos recién visibles, y agregarlas a la hoja de impresión.

### Main Flow
1. El usuario abre WooTag con sesión de Firebase iniciada y una tienda WooCommerce activa.
2. WooTag lee todos los productos publicados de la tienda (solo los campos necesarios: id, sku, regular_price, sale_price). Los productos ocultos se omiten.
3. WooTag carga de Firestore el snapshot de esa tienda (último precio reconocido por producto).
4. WooTag compara ambos y arma la lista de pendientes con dos tipos: **cambio de precio** (regular o de oferta distinto del snapshot) y **nuevo** (producto sin entrada en el snapshot, incluido el que pasó de oculto a visible).
5. Si hay pendientes, WooTag muestra un aviso con la cantidad y acceso a la lista.
6. El usuario revisa la lista, selecciona los productos y los agrega a la hoja de impresión.
7. Al imprimir, WooTag actualiza en Firestore el snapshot de esos productos con el precio impreso.
8. El usuario puede descartar un pendiente sin imprimirlo; WooTag actualiza igual el snapshot con el precio actual de ese producto.

## Ambiguity Log
- [x] Productos ocultos: se omiten. Si un producto pasa a ser visible, se trata como nuevo (decidido por el usuario el 2026-10-11).
- [x] Almacenamiento del snapshot: Firestore, que WooTag ya usa (decidido por el usuario el 2026-10-11). Hoy WooTag usa solo las colecciones `users` y `rooms`; la ruta del snapshot se define en Entities Affected.
- [x] Alcance de la detección: toda diferencia de precio contra el snapshot, haya impreso etiqueta o no (decidido por el usuario el 2026-10-11).
- [ ] Main Flow 7-8: ¿confirmás que un pendiente sale de la lista solo al imprimirlo o descartarlo? Propuesta: si el snapshot se actualizara al leer, un cambio no atendido desaparecería al día siguiente sin avisar.
- [ ] Main Flow 3-4: primer arranque, sin snapshot. ¿WooTag pide confirmar "tomar los precios actuales como ya al día" y guarda esa base sin listar nada? Sin esa regla, los +1.000 productos aparecerían como nuevos.
- [ ] Main Flow 1: usuario sin cuenta (modo invitado). Con el snapshot en Firestore, ¿la función no está disponible para invitados, o se ofrece una versión local? Propuesta: no disponible, con un aviso que invite a iniciar sesión.
- [ ] Main Flow 4: clave de comparación. ¿SKU o id de producto? WooTag usa el id como SKU cuando este falta (`wooService.ts`, `mapWooProduct`), y un SKU editado en la tienda aparecería como producto nuevo. Propuesta: clave por id de producto.
- [ ] Main Flow 2: productos variables. Su precio vive en las variaciones, y `mapWooProduct` hoy los importa con precio 0 (ver FIX-0007). ¿Se incluyen sus variaciones o se omiten los variables en esta versión?
- [ ] Main Flow 2, 4: ocultar y volver a publicar entre dos aperturas de WooTag no se detecta, porque WooTag solo ve el estado al abrirse. En ese caso el producto no se marcaría como nuevo. ¿Se acepta esa limitación?
- [ ] Main Flow 2: leer +1.000 productos exige paginar (unas 11 peticiones de 100). Hoy `fetchProductsByCategory` no pagina (FIX-0006). ¿FIX-0006 se aprueba antes que este contrato, o el FEAT incluye su propia lectura paginada del catálogo?
- [ ] Entities Affected: las reglas de Firestore no están en el repo (ver FIX-0003). ¿Se revisan las reglas de la ruta del snapshot dentro de este contrato o en un work item aparte?
